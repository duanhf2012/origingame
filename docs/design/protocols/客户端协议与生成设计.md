# OriginGame 客户端协议与生成设计

> 状态：目录、封包、生成规则、玩家登录结果、顶号推送与GameService消息注册方案已确认
> 更新日期：2026-08-15

## 1. 目录

客户端与服务端共享的 Protobuf 契约统一平铺在：

```text
protocol/common/
├── errorcode.proto
└── errorcode.pb.go
```

后续只在出现真实协议时增加`messageid.proto`、`playerlogin.proto`、`player.proto`等具体文件，当前不按版本或业务域增加子目录。

`.proto` 是唯一协议源；服务端 `.pb.go` 与源文件同目录并提交仓库。Protobuf 包固定为 `origingame.protocol`，Go 包固定为 `origingame/protocol/common;commonpb`。

## 2. 内容边界

`protocol/common` 只保存客户端需要共同理解的枚举和消息，包括客户端错误码、消息 ID、请求、响应及服务端主动推送。以下内容不得进入该包：

- MongoDB BSON 文档；
- 只供 HTTP 使用的 JSON DTO；
- Service 内部运行状态；
- Service 间 RPC 专用参数。

HTTP 可以在已经确认的接口中使用客户端错误码数值，但 HTTP DTO 不因此成为 Protobuf 契约。

### 2.1 应用层封包

TCP、KCP和WebSocket使用相同的`ApplicationPacket`，Body首期只使用Protobuf：

```text
客户端请求或服务端主动推送：
[uint16 MessageID][uint32 Sequence][Protobuf Body]

服务端请求响应：
[uint16 MessageID][uint32 Sequence][int32 ErrorCode][Protobuf Body]
```

TCP和KCP由Origin网络Module在`ApplicationPacket`外增加四字节大端长度帧，长度不包含自身；WebSocket直接使用自身Message边界。服务端主动推送固定`Sequence = 0`，客户端请求Sequence从1开始。`ErrorCode`只存在于请求响应，0表示成功。首期不增加Flags、压缩或动态Codec字段；需要兼容扩展时先设计新的协议版本边界。

### 2.2 MessageID与Gateway登录请求

`MessageID`不增加`MESSAGE_ID_`前缀，不使用全大写下划线风格；枚举值使用大驼峰。首期公共消息为：

```proto
enum MessageID {
  Ok = 0;                 // 成功且没有响应Body时使用的通用响应
  LoginPlayerReq = 1;     // 客户端请求登录玩家
  LoginPlayerRes = 2;     // 玩家登录成功数据或登录错误响应
  PlayerHeartbeatReq = 3; // 客户端玩家逻辑心跳
  PlayerKicked = 4;       // 玩家被其他连接顶号的主动推送
}
```

`MessageID = Ok`只表示“本次请求成功且没有响应Body”的通用响应，不能用于客户端请求或服务端主动推送。成功且需要返回数据时仍使用具体响应MessageID，例如登录成功使用`LoginPlayerRes`；请求是否成功最终仍由响应头`ErrorCode`判定，`ErrorCode = OK`表示成功。

客户端连接Gateway后的登录请求为：

```proto
// LoginPlayerRequest携带进入显示区服所需的客户端凭证。
message LoginPlayerRequest {
  string token = 1;        // LoginService签发的JWT
  int64 show_area_id = 2;  // 客户端选择的显示区服ID
}

// PlayerHeartbeatRequest是玩家在线后的逻辑心跳，Body没有业务字段。
message PlayerHeartbeatRequest {}
```

客户端不得提交`AccountID`、`RealAreaID`、`GatewayNodeID`或`GatewayConnectionID`。Gateway从JWT取得`AccountID`，从区服快照取得`RealAreaID`，并生成连接ID。

### 2.3 玩家登录结果

玩家连接Gateway并成功进入GameService后，登录响应Body使用：

```proto
// LoginPlayerResult是玩家进入GameService成功后的客户端登录数据。
message LoginPlayerResult {
  RoleInfo role_info = 1; // 玩家常用公共基础数据

  // 其他首屏确实需要的数据按业务增加独立结构。
}

// RoleInfo保存客户端经常使用的角色公共数据。
message RoleInfo {
  string account_id = 1;   // 账号ID
  int64 show_area_id = 2;  // 显示区服ID
  string nickname = 3;     // 玩家昵称
  int32 level = 4;         // 玩家等级
  int64 created_at_ms = 5; // 角色创建Unix毫秒时间
}
```

`LoginPlayerRequest`、`LoginPlayerResult`和`RoleInfo`计划放入`protocol/common/playerlogin.proto`。Gateway将客户端请求转换为内部`rpcapi.LoginPlayerRequest`；两者属于不同包，不直接复用。GameService的登录RPC直接使用`*commonpb.LoginPlayerResult`作为顶层返回值，Gateway只作为客户端`LoginPlayerRes`响应Body转发。

登录成功时Gateway写入`MessageID = LoginPlayerRes`、原请求`Sequence`和`ErrorCode = OK`，Body直接使用`LoginPlayerResult`。登录失败时仍使用`LoginPlayerRes`，写入具体`ErrorCode`且Body为空。登录结果不通过GameService的`Session.Reply`或`SendClientMessage`下行。

`role_info`固定保存上述公共角色数据。背包、任务等其他数据只有确定属于首屏登录结果时才增加各自结构字段；不要求每个Player Proxy都写入登录结果。不属于首屏的数据通过后续业务消息按需同步。样板工程不增加经验、战力、头像等非必要字段。

### 2.4 顶号推送

新连接登录同一Player时，GameService通知旧Gateway向旧连接发送专用主动推送，写完后关闭连接：

```proto
// PlayerKickedNotify通知客户端当前连接被其他登录替换。
message PlayerKickedNotify {
  ErrorCode reason = 1; // 断开原因，顶号时为LOGGED_IN_ELSEWHERE
}
```

该消息使用`MessageID = PlayerKicked`和主动推送格式，`Sequence = 0`，因此原因位于Protobuf Body，不使用只属于请求响应头的`ErrorCode`字段。GameService消息注册方式见[GameService设计](../services/GameService设计.md#83-显式消息注册)。

## 3. 兼容规则

- 已发布字段号和枚举值不得改变含义或分配给其他成员；
- 删除字段或枚举时必须保留原编号和名称；
- 新客户端必须能把未知错误码降级为通用内部错误；
- 不兼容变更必须先设计新的协议版本边界，不能直接修改现有线上含义。

后续业务MessageID只在出现真实客户端消息时按序增加，不预建空枚举值或代码生成器。GameService由PlayerModule创建实例化Router，显式调用`messagehandler.Register(router)`后冻结；注册表不使用包级可变状态或`init()`隐式注册。Gateway不理解普通玩家业务消息，由GameService Router负责其MessageID校验、Protobuf解码和Handler路由。

### 3.1 Sequence规则

- 客户端在每条连接上从1开始递增生成`uint32 Sequence`，0固定保留给服务端主动推送；达到最大值后回绕到1；
- 客户端维护当前连接的Pending Sequence，仍在Pending中的值不得复用；请求超时后移除，后续迟到响应直接忽略；
- 连接断开后该连接全部Sequence失效，新连接重新从1开始；
- Sequence只负责请求与响应关联，不承担通用请求去重或业务幂等；重要写业务使用独立业务请求ID。

## 4. 生成

生成环境固定使用 `protoc 24.0` 和 `protoc-gen-go 1.31.0`。Windows 执行 `scripts\generate.bat`，Linux/macOS 执行 `scripts/generate.sh`；提交前执行对应的 `scripts/check-generated.*`，确认生成物与源文件一致。

生成代码不得手工修改。升级生成器版本必须单独评估并提交全部可重复生成的差异。
