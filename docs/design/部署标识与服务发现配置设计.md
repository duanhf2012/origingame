# OriginGame v3 部署标识与服务发现配置设计

> 状态：当前工程已采用 Origin 内置服务发现和 Origin TCP RPC
> 更新日期：2026-08-26
> 上位文档：[OriginGame v3 总体架构设计](总体架构设计.md)

## 1. 目标与边界

本文档统一规定 OriginGame 的 NodeID、Node Labels、实际 ServiceName、Service 模板实例、服务发现可见范围和配置文件归属。它解决的是“实例如何命名、如何被发现、如何从候选集合中定位正确部署范围”，不替代业务路由：

- NodeID 是一个运行节点的稳定基础设施身份；
- 实际 ServiceName 表示该节点提供的能力或数据域；
- Node Labels 表示该节点所属的静态部署范围；
- `allow_discovery` 决定启用服务发现的调用 Node 可以看见哪些远端候选；
- RPC 路由再从可见候选中选择一个实例，或通过精确 NodeID 定向调用；
- Redis 在线玩家归属、GameService 动态负载和实例租约仍遵循[在线玩家归属设计](在线玩家归属设计.md)，不放入静态 Labels。

首期不引入独立配置中心、服务别名注册表或根据 NodeID 字符串解析业务归属。服务发现和业务代码必须读取明确的 ServiceName 与 Labels；NodeID 中保留部署信息只用于唯一标识、日志和运维定位。

当前运行配置固定使用 Origin 内置服务发现和 TCP RPC：`discovery.type` 为 `origin`，由 `discovery.origin.server.node` 指定唯一的 `DiscoveryService` Node；顶层 `rpc.transport` 为 `tcp`，每个 Node 通过 `rpc.tcp.listen` 和 `rpc.tcp.advertise` 声明独立的 TCP 地址。etcd、NATS 不再承担当前工程的服务发现或服务间 RPC。

纯客户端隔离 Node（当前为 `test-robot-1`）例外：其 Node 配置必须显式写 `discovery_enabled: false`。该 Node 不创建 Origin Discovery Provider 或系统 RPC，不发布本地 Service，也不能调用 Origin 内部 RPC；它仅通过 Login HTTP 和 Gateway TCP 等客户端外部入口访问已经独立运行的被测服务，因此单独启动时不要求包含 `DiscoveryService` Node。

## 2. 标识层次

| 标识 | 示例 | 稳定语义 | 是否参与业务筛选 |
| --- | --- | --- | --- |
| NodeID | `area1-game-1` | 一个逻辑部署槽位的集群内唯一身份 | 只用于精确定向和运维，不解析字符串做范围判断 |
| 实际 ServiceName | `GameService`、`AccDBService` | 对外提供的能力或数据域 | 是，RPC和服务发现首先按它定位服务 |
| Service模板名 | `DBService` | 创建Go实例并关联RPC契约的类型模板 | 否，不参与运行期发现和路由 |
| Node Label | `scope=area`、`real_area_id=1` | Node所属的静态部署范围 | 是，用于发现预筛选和RPC候选过滤 |
| Node启动会话 | `NodeSessionID` | Origin为一次Node进程启动生成的随机非零身份 | 用于RPC发现、Redis实例租约和旧进程隔离，不进入Node Labels |
| PlayerKey | `AccountID + ShowAreaID` | 玩家的稳定业务身份 | 用于DBService稳定路由和在线玩家归属 |

这些标识不能互相替代。特别是：

- `ShowAreaID` 是玩家身份和数据显示隔离的一部分，不是GameService部署范围，因此不配置为Node Label；
- `RealAreaID` 表示当前运行归属，必须通过Label显式表达，不能只从NodeID中截取；
- Node进程重启时可以复用同一个NodeID，但Origin生成的`NodeSessionID`必须变化；OriginGame不再另行生成`GameServiceInstanceID`；
- `NodeSessionID`由Origin生成并通过只读Node API提供给所属Service，业务配置不得设置或覆盖；若当前Origin版本尚未公开该值，实现GameService注册前必须先补充最小只读访问接口；
- 实际ServiceName不能追加区服号或实例序号，否则调用方无法用稳定的服务能力名称发现全部实例。

## 3. NodeID 规范

Origin要求NodeID为63字节以内的小写kebab-case。OriginGame固定使用以下格式：

```text
非区服Node：<scope>-<kind>-<ordinal>
区服Node：area<real-area-id>-<kind>-<ordinal>
```

首期保留的`kind`如下：

| kind | Node职责 | 示例 |
| --- | --- | --- |
| `login` | 公共HTTP登录入口 | `pub-login-1` |
| `gateway` | 公共客户端长连接入口 | `pub-gateway-1` |
| `db` | 承载模板化DBService实例 | `pub-db-1`、`area1-db-1` |
| `game` | 承载一个真实区服的GameService | `area1-game-1`、`area1-game-2` |
| `<business>` | 后续真实存在的公共、区服或隔离测试业务Node | `pub-recharge-1`、`test-robot-1` |

命名规则：

1. 范围位于NodeID第一段：公共Node固定为`pub`，隔离测试Node使用`test`，区服Node使用`area<RealAreaID>`（例如`area1`）；`ordinal`是同一`kind + scope + RealAreaID`内从1开始的稳定部署序号，不补前导零；
2. 数字型`RealAreaID`使用无前导零的十进制文本；非数字ID必须先规范化为符合NodeID约束的稳定小写kebab-case标识；
3. 同一服务发现命名空间内NodeID必须唯一；同一个逻辑部署槽位正常重启可以复用原NodeID；
4. 滚动发布中新旧实例需要同时存活时必须使用不同`ordinal`，不能抢占仍存活的NodeID；
5. NodeID不包含IP、端口、主机名、Pod UID、构建版本和随机启动值；
6. 不使用`LoginServer1_pub`、`GameServer1_area_1`等大写或下划线形式，也不保留无意义的`Server`后缀；仓库只有一个生产程序，Node职责已经由`kind`表达；
7. 业务代码禁止通过拆分NodeID取得`RealAreaID`、服务类型或其他路由条件。

## 4. Node Labels 规范

首期只定义两个Label键：

| Label | 必填范围 | 允许值 | 说明 |
| --- | --- | --- | --- |
| `scope` | 全部Node | `pub`、`area`、`test` | 公共、真实区服或隔离测试部署范围 |
| `real_area_id` | `scope=area` | RealAreaID的规范字符串 | 当前真实区服运行归属；数字值在YAML中也必须加引号 |

示例：

```yaml
labels:
  scope: pub
```

```yaml
labels:
  scope: area
  real_area_id: "1"
```

校验规则：

- `scope=pub`或`scope=test`时禁止配置`real_area_id`；
- `scope=area`时必须配置非空`real_area_id`；
- 同一RealAreaID的Game Node和DB Node使用完全相同的`real_area_id`文本；
- Label键和值区分大小写，OriginGame统一使用小写snake_case键和上述规范值；
- Labels是启动期冻结的静态部署元数据，改变范围必须重启Node；
- 不把Ready、Draining、负载、在线数、容量、租约、启动实例ID和版本号放入Labels；
- 首期不增加`server_kind`，因为目标能力已经由实际ServiceName精确表达；
- 首期不增加`environment`，开发、测试和生产环境使用不同的服务发现namespace或network隔离；
- 后续只有出现真实筛选需求时才增加Label，不能把Labels发展成重复配置数据库或业务状态的通用Map。

## 5. 实际 ServiceName 与模板实例

普通Service的实际名称保持与模板名一致：

| 能力 | Node中的Service声明 | 实际ServiceName |
| --- | --- | --- |
| 登录 | `LoginService` | `LoginService` |
| 长连接网关 | `GatewayService` | `GatewayService` |
| 区服游戏逻辑 | `GameService` | `GameService` |

DBService只实现一个`DBService`模板，按数据域使用两个固定实际名称：

```yaml
services:
  - "AccDBService:DBService"
  - "RoleDBService:DBService"
```

| 实际ServiceName | 模板名 | 数据域 |
| --- | --- | --- |
| `AccDBService` | `DBService` | 账号、登录协调、GameService注册和在线玩家归属使用的账号MongoDB与公共Redis |
| `RoleDBService` | `DBService` | 当前RealAreaID的角色MongoDB与区服Redis |

所有Node上的同类能力必须复用相同实际ServiceName：

- 不使用`AccDBService1`、`RoleDBService1`、`GameServiceArea1`等名称；
- 服务发现、RPC和业务配置都使用实际ServiceName，不使用`DBService`模板名查找运行实例；
- 同一个Node最多存在一个同名实际Service实例；需要更多副本时增加Node，而不是在同一Node发明带序号的ServiceName；
- `AccDBService`和`RoleDBService`虽然使用同一Go模板，但配置、连接池、队列、并发额度和资源生命周期相互独立。

## 6. 首期部署拓扑

首期固定以下装配关系：

| Node类型 | Labels | 必须装配的Service |
| --- | --- | --- |
| `pub-login-N` | `scope=pub` | `LoginService` |
| `pub-gateway-N` | `scope=pub` | `GatewayService` |
| `pub-db-N` | `scope=pub` | `AccDBService:DBService` |
| `areaR-game-N` | `scope=area, real_area_id=R` | `GameService` |
| `areaR-db-N` | `scope=area, real_area_id=R` | `AccDBService:DBService`、`RoleDBService:DBService` |

所有`AccDBService`连接同一账号MongoDB和公共Redis，但调用范围按部署层隔离：

- LoginService、GatewayService和公共业务Service默认只使用`scope=pub`的`AccDBService`；
- GameService默认只使用与自己`real_area_id`相同的区服DB Node上的`AccDBService`和`RoleDBService`；
- 不自动从区服AccDBService故障切换到公共或其他区服AccDBService。跨范围回退会绕过容量与故障隔离，若以后确有需要必须单独设计熔断、容量和恢复策略；
- 公共范围AccDBService实例全部故障时暂停公共入口的新登录协调；某个区服范围的AccDBService实例全部故障时暂停该区服GameService发起的登录协调；公共账号数据库或公共Redis故障时所有范围都暂停新的登录协调。已经在线的区服业务仍尽量依赖本区服RoleDBService继续运行。

一个逻辑区服可以各自部署多个`areaR-game-N`和`areaR-db-N`副本。副本数量不进入名称规则或业务协议，由部署配置和容量规划决定。

## 7. 服务发现可见范围

`allow_discovery`是调用Node的候选可见范围，不是最终的单实例路由策略。生产配置必须显式声明最小需要范围；省略字段会发现全部公开远端Service，只适合早期本地调试。

首期每套开发、测试或生产环境使用一个共享的逻辑服务发现namespace或network，该环境中的公共Node和全部区服Node都注册在同一发现范围。区服隔离使用`scope`和`real_area_id`完成，不为每个区服建立独立发现network；否则公共Service要发现全部区服时必须维护不断增长的`watch_networks`列表。不同环境必须使用不同namespace或network，不能依赖`environment` Label防止跨环境调用。以后出现真实的跨地域、Cell或超大规模目录隔离需求时再重新设计多network拓扑。

首期依赖矩阵：

| 调用方 | 允许发现的目标 | Node Label条件 | 用途 |
| --- | --- | --- | --- |
| LoginService | `AccDBService` | `scope=pub` | 账号、区服目录和登录限流 |
| GatewayService | `AccDBService` | `scope=pub` | 玩家归属查询和原子分配 |
| GatewayService | `GameService` | `scope=area` | 可以接收Redis返回的任意区服精确NodeID |
| GameService | `AccDBService` | `scope=area`且相同`real_area_id` | 注册、负载、在线归属和登录协调 |
| GameService | `RoleDBService` | `scope=area`且相同`real_area_id` | 当前区服角色MongoDB和Redis |
| 需要跨区工作的公共Service | `GameService` | `scope=area` | 发现全部区服候选；具体业务路由在对应Service设计中定义 |
| DB Node | 无 | `allow_discovery: []` | 首期只提供数据能力，不主动调用远端业务Service |
| Robot Node | 无 | `discovery_enabled: false` | 只使用客户端 HTTP/TCP 外部入口，不创建或使用 Origin 服务发现 |

公共Service需要发现全部区服GameService时，`allow_discovery`只写`scope=area`，不列举每个RealAreaID。调用某个指定区服时，再由RPC Client使用一个或多个Labels筛选候选；这样新增区服不需要修改公共Service的发现白名单。

发现规则之间是OR，同一规则内不同Label键是AND。以区服1为例，逻辑合并后的Node配置如下：

```yaml
nodes:
  - id: pub-login-1
    labels: {scope: pub}
    allow_discovery:
      - services: [AccDBService]
        node_labels: {scope: pub}
    services: [LoginService]

  - id: pub-gateway-1
    labels: {scope: pub}
    allow_discovery:
      - services: [AccDBService]
        node_labels: {scope: pub}
      - services: [GameService]
        node_labels: {scope: area}
    services: [GatewayService]

  - id: pub-db-1
    labels: {scope: pub}
    allow_discovery: []
    services:
      - "AccDBService:DBService"

  - id: area1-game-1
    labels: {scope: area, real_area_id: "1"}
    allow_discovery:
      - services: [AccDBService, RoleDBService]
        node_labels: {scope: area, real_area_id: "1"}
    services: [GameService]

  - id: area1-db-1
    labels: {scope: area, real_area_id: "1"}
    allow_discovery: []
    services:
      - "AccDBService:DBService"
      - "RoleDBService:DBService"
```

上例用于说明规则的完整逻辑视图。实际部署可以只启动其中一个或一组Node，但同一个`--config`目录内不能用多个可加载文件重复定义顶层`nodes`路径。

## 8. RPC 路由规则

服务发现和RPC路由按以下顺序工作：

```text
实际ServiceName
    -> allow_discovery保留当前Node有权看见的远端实例
        -> RPC调用需要时按Node Labels进一步筛选部署范围
            -> Route(dispatchKey)或现有默认策略选择一个实例
                -> OnNode(nodeID)用于已有精确归属的定向调用
```

具体规则：

1. 调用DBService时，实际ServiceName先选择`AccDBService`或`RoleDBService`数据域，Labels再限定`pub`或指定RealAreaID，最后使用同一个业务Key执行`Route(dispatchKey)`并把该Key作为请求`dispatch_key`；
2. Gateway登录分配不按Labels自行选择最低负载GameService。它通过公共AccDBService执行Redis原子分配，取得精确`GameServiceName + NodeID + NodeSessionID`后使用`OnNode(nodeID)`；首次加载的条件更新与失败回滚另外匹配全局唯一`GatewayConnectionID`；
3. 首期只有Gateway登录使用Redis玩家归属和`OnNode(nodeID)`精确调用GameService；其他公共Service出现真实在线调用需求后再定义查询与重试契约，不能仅用Label猜测玩家当前归属；
4. 公共Service执行“区服级、任意一个GameService均可处理”的无玩家归属调用时，才按`scope=area + real_area_id=R`筛选候选，再使用稳定Key、轮询、随机或框架默认策略选择实例；
5. Labels没有匹配节点时返回无路由错误，不回退到其他区服或全量候选；
6. Origin框架正在单独增加RPC Client按Labels筛选候选的公共能力。OriginGame接入时以框架最终确认的API名称为准，但不得改变本节两阶段语义。

## 9. 配置文件与配置归属

配置继续遵循仓库平铺规则：

| 文件 | 内容 |
| --- | --- |
| `<node-id>-node.yaml` | 单Node生产部署的拓扑、Labels、`allow_discovery`和Service装配 |
| `local-node.yaml` | 本地确需单进程启动多个Node时的唯一拓扑文件 |
| `loginservice.yaml` | LoginService公共业务配置 |
| `gatewayservice.yaml` | GatewayService公共业务配置 |
| `gameservice.yaml` | GameService配置；不同RealAreaID的差异放`node_services` |
| `dbservice.yaml` | 各实际DBService的完整MongoDB、Redis、容量和受控扩展配置 |
| `discovery.yaml` | Origin 内置服务发现类型、DiscoveryService Node 和租约 |
| `rpc.yaml` | Application 级 RPC 传输类型和 TCP 公共参数 |
| `*.yaml.example` | 不参与加载的生产参考配置 |

一个运行时`--config`目录只能有一个文件拥有顶层`nodes`路径。生产通常为每个部署实例准备独立配置目录，其中只放自己的`<node-id>-node.yaml`；仓库本地多Node联调则使用一个`local-node.yaml`集中声明全部Node。不能把多个`*-node.yaml`同时放进同一个加载目录并期待数组自动追加。

普通且所有实例相同的业务配置放`services.<实际ServiceName>`。与Node、RealAreaID、数据库地址或数据域绑定的配置放`node_services.<NodeID>.<实际ServiceName>`。Origin对Node专属Service块采用整块选择，不与公共块递归合并，因此每个Node专属块必须完整。

DBService模板实例只按实际ServiceName读取配置，不回退`services.DBService`：

```yaml
node_services:
  area1-db-1:
    AccDBService:
      max_io_concurrency: 64
      max_inflight_requests: 128
      mongodb:
        uri: "mongodb://192.168.8.3:27017/?appName=acc-area1-db-1&maxPoolSize=64"
        database: origingame_account
      redis:
        addresses: ["192.168.8.3:6379"]
        client_name: origingame-acc-area1-db-1
        database: 0

    RoleDBService:
      max_io_concurrency: 64
      max_inflight_requests: 128
      mongodb:
        uri: "mongodb://192.168.8.3:27017/?appName=role-area1-db-1&maxPoolSize=64"
        database: origingame_role
      redis:
        addresses: ["192.168.8.3:6379"]
        client_name: origingame-role-area1-db-1
        database: 1
```

示例地址仅说明配置归属，不复制Redis Module全部可选字段。生产凭证由部署Secret注入，不提交真实密码、Token或密钥。即使两个实例暂时连接同一MongoDB或Redis地址，也必须保留两个完整配置块和独立Client名称，不能通过模板名共享运行配置。

## 10. 启动校验与运维要求

Origin已有的NodeID、Label和Service声明校验之外，OriginGame装配层还必须在生命周期启动前校验：

1. 每个公开Node都具有合法`scope`；
2. `scope`与`real_area_id`满足第4节组合规则；
3. `areaR-game-N`和`areaR-db-N`中的运维名称与Label声明一致，但业务运行时仍只使用Label；
4. `pub-db-N`只装配`AccDBService`，`areaR-db-N`同时装配`AccDBService`和`RoleDBService`；
5. GameService自身配置的RealAreaID与Node Label一致；
6. DBService配置路径使用实际ServiceName，两个数据域的MongoDB数据库、Redis逻辑数据库、Client名称和连接资源符合[DBService设计](services/DBService设计.md)；
7. 生产Node显式配置`allow_discovery`，不得因省略而意外发现全部公开服务；
8. 同一环境的公共Node和区服Node使用已经确认的同一个服务发现namespace或network；
9. 同一服务发现namespace或network中不存在重复NodeID。

日志、监控和管理接口统一输出`node_id`、`service_name`、`scope`，区服Node再输出`real_area_id`。敏感连接信息不得随配置错误或诊断输出泄漏。

## 11. 已确认结论

- NodeID固定为非区服`<scope>-<kind>-<ordinal>`或区服`area<real-area-id>-<kind>-<ordinal>`，范围必须位于第一段；
- 首期Node Labels只使用`scope`和区服必需的`real_area_id`；
- 实际ServiceName表达能力，Labels表达范围，业务不得解析NodeID做路由；
- DBService模板固定实例化为`AccDBService`和`RoleDBService`，不在名称中追加区服号；
- 公共DB Node只部署AccDBService，每个区服DB Node同时部署AccDBService和本区服RoleDBService；
- 公共调用方默认使用公共AccDBService，GameService默认使用本区服AccDBService和RoleDBService，不做跨范围自动回退；
- 公共Service通过`allow_discovery`发现全部区服GameService，新增区服不修改发现白名单；指定区服调用由RPC运行期Label筛选完成；
- 每套环境首期只使用一个共享服务发现namespace或network，环境间通过namespace或network隔离；
- Gateway登录发现已有玩家归属时，通过Redis取得精确NodeID后使用`OnNode`，不使用Label路由猜测归属；
- Node专属Service配置使用实际ServiceName并整块定义，模板实例不回退模板名配置。
- 当前服务发现使用唯一的`DiscoveryService` Node，服务间 RPC 统一使用TCP；每个启用的Node都必须配置唯一的`listen`和可达`advertise`地址。
- etcd和NATS仅可作为本地可选基础设施保留，不得重新作为当前服务发现或服务间RPC的隐式依赖。
