# OriginGame v3 在线玩家路由设计

> 状态：首期登录查找、分配、驻留和Redis原子协调已确认
> 更新日期：2026-08-15

## 1. 目标与边界

本设计解决以下问题：

1. 同一玩家不能同时被两个 GameService 实例承载；
2. Gateway 登录时可以原子选择负载合适的 GameService；
3. GameService 宕机、重启和玩家重登时，不把登录请求或客户端消息交给旧进程、旧连接。

Redis 是在线协调和路由目录，不保存玩家持久化业务数据。本设计不重新引入集中式 CenterService，也不建设 SessionService。

## 2. 玩家路由身份

当前玩家使用以下二元组作为稳定路由身份：

```text
PlayerKey = AccountID + ShowAreaID
```

全部区服角色文档混合存放在同一个角色数据库中，`ShowAreaID` 是角色与玩家身份的显式隔离字段。同一账号在不同显示区服属于不同玩家；所有面向指定玩家的内部请求必须使用`AccountID + ShowAreaID`或由二者生成的稳定`PlayerKey`，不能只使用昵称或当前`RealAreaID`。

`RealAreaID` 由当前 `ShowAreaID -> RealAreaID` 映射得到，只表示玩家当前运行归属、GameService候选分组和Redis Hash Tag，不能改变 `PlayerKey`。由于首期Redis路由Key包含`RealAreaID`，不支持在线热切换映射：合服或映射调整必须先停止对应显示区服的新登录，排空在线Player和旧路由，再切换映射并开放登录。

## 3. Redis 路由记录

推荐键名：

```text
{area:<RealAreaID>}:player-route:<ShowAreaID>:<AccountID>
{area:<RealAreaID>}:game-services
{area:<RealAreaID>}:game-service:<NodeID>:<NodeSessionID>
{area:<RealAreaID>}:game-service-lease:<NodeID>:<NodeSessionID>
```

以上键全部位于公共 AccDBService 使用的 Redis，不进入任何区服 RoleDBService Redis。同一真实区服相关键使用相同 Redis Cluster Hash Tag，为以后切换 Redis Cluster和执行同槽原子分配保留空间；当前首期仍使用Standalone或Sentinel。玩家路由值至少包含：

| 字段 | 说明 |
| --- | --- |
| `real_area_id` | 真实区服 ID |
| `show_area_id` | 显示区服 ID，PlayerKey组成部分 |
| `account_id` | 账号 ID，PlayerKey组成部分 |
| `state` | `ASSIGNING`、`LOADING`、`ONLINE`、`RESIDENT`或`LEAVING` |
| `gs_service` | GameService 逻辑服务名 |
| `gs_node_id` | Origin RPC 精确定向调用所需的 NodeId |
| `gs_node_session_id` | Origin为GameService所在Node本次启动生成的会话标识 |
| `assignment_connection_id` | `ASSIGNING/LOADING`阶段的全局唯一Gateway连接ID；进入`ONLINE`后清除 |
| `updated_at_ms` | 最近一次成功续租时间 |

路由记录必须有租约或TTL，并由承载玩家的GameService使用比较并续租的原子操作刷新。续租时必须同时匹配`gs_node_id + gs_node_session_id`，旧进程不能覆盖新进程路由。GameService实例另有独立的带TTL存活租约；登录分配脚本不能只相信候选有序集合中的残留成员，必须同时确认实例状态为`READY`且租约仍存在。

首期不支持在线Player跨GameService迁移，不增加玩家级`SessionFence`或`RouteVersion`。不同客户端登录同一Player时仍进入当前GameService，由全局唯一`GatewayConnectionID`完成登录幂等、顶号和旧连接消息校验。

`ONLINE`表示Player绑定有效客户端连接；`RESIDENT`表示连接已断开，但Player仍在原GameService内驻留。Gateway登录分配必须把租约有效的`ONLINE`和`RESIDENT`都视为已有归属，不得重新选择GameService；`ASSIGNING`、`LOADING`和`LEAVING`只返回`WAIT`，不得作为可登录目标。

首版每个Player只有一个默认GameService路由，不增加路由名称或命名路由表。跨服战斗等后续业务如果需要额外目标，应设计独立业务路由，不复用或扩张玩家登录归属。

## 4. PlayerRouteStore 与 DBService 边界

`PlayerRouteStore` 是 GatewayService和GameService进程内的普通组件，不是 Origin Module、独立 Service 或权威内存路由表。它不持有Redis Client、连接池、Timer和后台goroutine，只负责构造Redis Key、登记Script调用参数并解释结果：

```text
PlayerRouteStore
    -> AccDBService RPC
        -> 公共Redis
```

Gateway和GameService的在线路由、GameService注册及负载操作全部通过AccDBService执行，不通过区服RoleDBService。Gateway使用`scope=pub`的AccDBService实例，GameService使用与自己`real_area_id`相同的区服DB Node上的AccDBService实例；两类实例属于同一账号数据域并连接同一公共Redis。请求使用`PlayerKey`作为非空`dispatch_key`，RPC Client同时使用`Route(PlayerKey)`；GameService实例注册和续租使用稳定的实例Key。DBService只执行登记Script或受限命令，不理解玩家路由业务。部署范围和发现规则见[部署标识与服务发现配置设计](部署标识与服务发现配置设计.md)。

Redis Script不形成新的领域RPC。`PlayerRouteStore`固定负责以下协议适配：使用第3节四类Key及相同`{area:<RealAreaID>}`Hash Tag，按Script登记名选择KEYS和ARGV顺序，构造通用`ExecuteRedis`请求，并把稳定整数返回码和位置字段转换为类型明确的Go结果。Gateway、GameService和DBService实现均不得自行拼接同一Script参数，也不得解析Redis字符串结果。Script源码由AccDBService启动时按固定名称登记，请求不能携带任意Lua源码或覆盖脚本约束。

GameService注册和租约续期需要持有Timer与停止流程，因此由GameService自身或其专属生命周期Module负责；不能把该生命周期塞入`PlayerRouteStore`。

## 5. GameService 注册与负载候选集

每个GameService实例在完成自身配置、本区服AccDBService、本区服RoleDBService和本地组件准备后，使用Origin为当前Node进程生成的`NodeSessionID`，并通过本区服AccDBService向公共Redis注册：

```text
RealAreaID
GameServiceName
GameServiceNodeID
GameServiceNodeSessionID
State = READY | DRAINING
OnlineCount
LoadingCount
ResidentCount
MaxPlayers
HeartbeatLease
```

注册信息的当前用途只限于Gateway登录分配：让Redis原子Script知道某个`RealAreaID`下有哪些可用实例、当前负载、容量和存活状态。其他业务Service首期不读取GameService负载注册表或玩家路由。

不采用GameService向所有Gateway广播动态负载作为权威分配依据。多个Gateway的快照会出现延迟和不一致，也无法在选择时原子预占容量，容易让并发登录同时涌向同一个最低负载实例。Origin服务发现只负责RPC可达性；Redis注册表负责登录候选、负载和原子预占。

首期相同容量GameService的负载值固定为：

```text
AssignedCount = LoadingCount + OnlineCount + ResidentCount
```

GameService使用必填配置`player_capacity`作为`MaxPlayers`，本地样例值为`5000`。该容量统计已经预占的`ASSIGNING`以及`LOADING`、`ONLINE`、`RESIDENT`玩家；配置缺失或非正数时GameService启动失败。

每个RealArea使用有序集合按`AssignedCount`排序。分配时先增加`LoadingCount`和`AssignedCount`完成预占；加载成功把`LoadingCount`转为`OnlineCount`；断线驻留把`OnlineCount`转为`ResidentCount`；重连再把`ResidentCount`转为`OnlineCount`。上述转换都不改变`AssignedCount`，只有加载失败或Resident最终释放时才减少Assigned。不同容量实例的归一化权重算法在出现真实需求后再设计，首期不提前增加。

GameService实例使用带TTL的独立存活租约并周期续租。候选有序集合不是存活事实；分配Script每次选取候选时必须检查`State == READY`、租约存在且`AssignedCount < MaxPlayers`，发现租约失效的残留成员时将其移出候选集并继续检查下一个有界候选。

### 5.1 普通Redis命令与原子Script边界

单条读取、单Key租约续期等不需要联合判断的操作使用普通Redis命令。只有同时查询、比较、修改多份状态或负载计数时才使用经AccDBService登记的短Lua Script。

原子Script的首期业务能力固定为：

| Script | 原子职责 |
| --- | --- |
| `RegisterGameService` | 登记或刷新当前`NodeID + NodeSessionID`实例、容量和候选集状态 |
| `SetGameServiceDraining` | 条件标记排空并从新分配候选集移除 |
| `AssignOrGetPlayer` | 查询已有归属，或选择最低负载实例、预占容量并写入`ASSIGNING` |
| `BeginPlayerLoad` | 按实例身份和连接ID将`ASSIGNING`条件改为`LOADING` |
| `CompletePlayerLogin` | 将`LOADING`转为`ONLINE`，或将原GameService的`RESIDENT`转为`ONLINE` |
| `ReleasePlayerLoad` | 按实例身份和连接ID条件回滚失败预占 |
| `MarkPlayerResident` | 按当前所有者将`ONLINE`转为`RESIDENT` |
| `BeginPlayerRelease` | 按当前所有者将到期`RESIDENT`改为`LEAVING`、扣减负载并设置5秒TTL |
| `RenewPlayerRoutes` | 按当前`NodeID + NodeSessionID`批量续租最多256条`ONLINE/RESIDENT`路由 |

使用Script的目的是保证上述多步状态转换原子性，不是用Lua承载通用业务。`MULTI/EXEC`不适合表达“根据前序查询结果分支、选择候选并比较更新”；首期也不引入需要客户端竞争重试的`WATCH`流程。Script不允许请求携带任意源码，必须短小、有界并使用Redis服务端真实时间。

### 5.2 首期固定时限与扫描上限

| 项目 | 固定值 | 说明 |
| --- | ---: | --- |
| GameService实例租约TTL | `15s` | 限制宕机实例仍可能被看见的时间窗口 |
| 实例续租周期 | `5s` | 保留短暂抖动余量 |
| `ASSIGNING`最长时间 | `10s` | 超时后才允许按条件回收 |
| `LOADING`最长时间 | `35s` | 略大于Gateway登录30秒总Deadline，避免失败状态长时间阻塞下一次登录 |
| 玩家路由TTL | `60s` | GameService定期续租，包含`ONLINE`和`RESIDENT` |
| 玩家路由批量续租周期 | `20s` | 在TTL内保留充足重试余量 |
| 单批玩家路由续租 | `256` | 限制单次Script工作量 |
| 分配候选扫描 | `16` | 负载最低成员中的有界检查数 |
| 单次过期残留清理 | `64` | 限制清理Script阻塞Redis的时间 |

上述值首期作为代码常量，不增加运行配置。玩家断线驻留时间另固定为15分钟；驻留期间GameService仍为`RESIDENT`路由批量续租。最终释放使用`LEAVING`固定5秒TTL封住跨GameService重复加载窗口，该状态不再续租。

## 6. Gateway 原子查找、分配与重试

Gateway验证Token并取得`AccountID + ShowAreaID`后，从当前有效区服快照解析`RealAreaID`，通过`PlayerRouteStore`调用AccDBService登记的`AssignOrGet` Redis Script。请求同时携带本次全局唯一`GatewayConnectionID`。查询已有玩家与选择新实例必须在同一次Script中完成，不能先查询再单独分配。

`AssignOrGet`原子执行：

1. 根据`PlayerKey`查询玩家路由；
2. 路由存在时检查状态、目标Node身份和实例租约：有效`ONLINE/RESIDENT`返回`EXISTING`及原精确GameService，`ASSIGNING/LOADING/LEAVING`返回`WAIT`，均不因新的Gateway连接重新分配GameService；
3. 旧路由已经失效时，按旧`NodeID + NodeSessionID`条件清理，不把它作为在线结果；
4. 从当前`RealAreaID`候选集合中选择未被本次尝试排除、状态为`READY`、租约有效、`AssignedCount`最小且未满的GameService；
5. 原子增加目标实例的`LoadingCount`和`AssignedCount`；
6. 写入带TTL的`ASSIGNING`路由，并把本次全局唯一`GatewayConnectionID`记录为`assignment_connection_id`；
7. 返回稳定决策码及必要路由字段。

`AssignOrGet`的稳定决策固定为：

| 决策 | 含义 |
| --- | --- |
| `EXISTING` | 已有有效`ONLINE/RESIDENT`归属，可以调用该GameService |
| `ASSIGNED` | 已完成新GameService预占，可以发起首次加载 |
| `WAIT` | 路由仍处于`ASSIGNING/LOADING/LEAVING`等不可重复分配阶段 |
| `NO_CAPACITY` | 当前没有满足租约、状态和容量条件的GameService |

Redis Script使用稳定整数返回码和固定位置字段；`PlayerRouteStore`负责转换为Go枚举与结构，Gateway和其他业务层不得解析Redis字符串或数组位置。

Gateway根据返回的精确实例发起Origin RPC。GameService收到首次加载请求后，使用自身`NodeID + NodeSessionID`以及请求中的`GatewayConnectionID`校验路由，将`ASSIGNING`条件更新为`LOADING`；角色数据加载及Player生命周期回调成功后再更新为`ONLINE`。加载失败必须使用相同`NodeID + NodeSessionID + GatewayConnectionID`条件释放路由与负载预占。

路由已经`ONLINE`或`RESIDENT`时，GameService不再执行数据加载：相同`GatewayConnectionID`幂等返回；`RESIDENT`直接绑定新连接并转为`ONLINE`；`ONLINE`收到不同连接登录时，先向旧`GatewayNodeID + GatewayConnectionID`提交顶号通知和写后断开请求，再替换Player当前连接。旧Gateway不可达不阻止新连接接管，旧连接的迟到消息由GameService按连接ID拒绝。

Gateway检测到连接关闭时使用`NotifyPlayerDisconnected`只提交全局唯一`GatewayConnectionID`；GameService通过实例内ConnectionID索引找到Player并条件转为`RESIDENT`。客户端在线后每5秒发送玩家逻辑心跳，GameService超过15秒未收到时主动转为`RESIDENT`并调用旧Gateway的`NotifyCloseClientConnection`。因此Gateway异常退出不增加独立实例租约或Gateway NodeSessionID绑定，心跳超时作为最终强对齐；Notify迟到或重复通过ConnectionID和Player状态幂等忽略。

驻留15分钟到期后，GameService完成一次最终存档；无论成功或失败，都使用`BeginPlayerRelease`把当前`RESIDENT`原子改为`LEAVING`并设置5秒TTL，然后执行本地`OnRelease`和Player移除。Gateway看到`LEAVING`只能在登录Deadline内等待重查，不能调用旧实例或选择新实例；TTL到期、旧Player已经释放后才允许重新分配。

同一次Gateway登录默认最多尝试三个不同GameService实例，作为代码固定上限，不新增配置。`AssignOrGet`接受有界的`ExcludedGameServiceInstances`，每项使用`NodeID + NodeSessionID`，避免实例租约尚未过期时重复选中已经明确失败的实例。以下确定未进入玩家加载的结果可以条件释放`ASSIGNING`预占并重试：

- Origin确认目标Service不存在或请求尚未发送；
- GameService明确返回`SERVICE_NOT_READY`、`SERVICE_DRAINING`或`SERVICE_FULL`；
- 目标GameService在校验并进入`LOADING`前明确拒绝。

RPC超时、请求发送后连接断开等结果属于执行状态未知，不能立即释放并选择第二个实例。Gateway必须重新查询玩家路由：已经`ONLINE`则继续使用该实例；返回`WAIT`时每`1s`查询一次；实例租约失效或`ASSIGNING/LOADING`超过确认的状态期限后，才允许由Redis Script原子回收并重新分配。全部查询、RPC和重试共同受`30s`登录总Deadline约束；Deadline内仍无法确认时返回暂时不可用，不能冒险形成两个玩家所有者。

条件释放接口至少校验：

```text
route.state == ASSIGNING
route.gs_node_id == ExpectedGameServiceNodeID
route.gs_node_session_id == ExpectedGameServiceNodeSessionID
route.assignment_connection_id == ExpectedGatewayConnectionID
```

任一字段不匹配都不得删除或减少负载，避免旧Gateway释放已经进入`LOADING/ONLINE`或后来使用同一GameService产生的新预占。

## 7. 精确实例校验

首期不支持在线Player跨GameService迁移，因此不为未来场景增加玩家级路由版本。不同客户端重登只替换当前GameService中的Gateway连接，不改变GameService归属。

Gateway登录调用目标GameService时，必须使用Redis返回的精确`NodeID + NodeSessionID`。目标GameService必须校验当前进程身份并确认本地Player状态：

- 一致且Player存在：当前实例拥有该玩家，可以处理；
- 玩家不在本实例：返回 `PLAYER_OFFLINE`；
- NodeSessionID不一致：返回`ROUTE_MOVED`，不能把旧进程路由交给重启后的新进程；
- 实例正在退出或恢复：返回 `SERVICE_NOT_READY`。

Gateway收到`ROUTE_MOVED`后丢弃旧结果，重新查询Redis再有限重试。登录、重连和顶号继续携带`GatewayConnectionID`，并由GameService与Player当前连接比较。

## 8. GameService 停止、宕机与重启

`NodeSessionID`由Origin使用安全随机源为每次Node进程启动生成，不能由业务配置，也不能只使用长期不变的服务名或NodeID。OriginGame不再另行生成`GameServiceInstanceID`。

GameService 启动和恢复遵守以下规则：

1. 完成配置、本区服AccDBService、本区服RoleDBService、服务发现和本地组件初始化前不进入Ready；GameService不直接组合MongoDB或Redis Module；
2. 通过AccDBService向公共Redis注册当前`NodeID + NodeSessionID`和带TTL租约的存活记录；
3. 清理或接管旧路由只能通过校验旧实例租约、路由状态、NodeSessionID以及加载阶段GatewayConnectionID的Redis原子操作完成；
4. 旧实例遗留玩家路由等待实例租约失效后，由分配Script按旧`NodeID + NodeSessionID`条件清理，不能直接当作在线；
5. 恢复完成并能安全承载新玩家后才开放新分配；
6. GameService定期按当前`NodeID + NodeSessionID`续租本地玩家路由。公共Redis暂时不可用时保留本地Player并继续不依赖AccDBService的在线业务；只有Redis明确返回所有权已经属于其他实例时，才停止该Player的新业务并执行冲突处理。

GameService 不需要在重启后伪造“之前玩家仍在线”。客户端重连成功、玩家数据重新加载并完成路由认领后，路由才重新变为 `ONLINE`。

正常停止时，GameService先在本地进入`DRAINING`，使新到达的登录在修改路由前明确失败；随后通过AccDBService原子把实例标记为`DRAINING`并从候选有序集合摘除，停止续租，在停止预算内处理已经进入的登录和在线玩家，最后条件清理实例注册。摘除前后无法形成跨进程绝对原子边界，竞态请求由Gateway的明确失败重试兜底。

异常宕机时，Redis中的实例注册在租约TTL到期前仍可能短暂有效。分配Script检查租约可以跳过已经过期的实例，但无法消除“Script检查租约后实例立即宕机”的瞬间；Gateway精确RPC失败后必须按第6节分类处理并有界重试。这个窗口由实例租约TTL限制。

## 9. 公共Redis故障边界

- Gateway无法通过AccDBService确认或修改路由时，新登录直接返回服务暂时不可用，不在本地选择GameService；
- GameService保留已经加载的Player，继续处理不依赖AccDBService的在线业务，不因一次或连续几次续租失败主动释放Player；
- Redis恢复后，GameService重新登记实例并继续按`NodeID + NodeSessionID`续租本地`ONLINE/RESIDENT`路由；
- Redis明确返回路由属于其他实例时，当前GameService才把它作为所有权冲突处理；
- 首期不增加进程内路由健康状态机，也不承诺Redis主节点无损自动切换。生产故障切换和数据恢复策略在实际部署Redis Sentinel前单独验证。

## 10. 首期实现范围

- 实现本设计列出的GameService注册、租约、玩家分配和状态转换Script，并为KEYS、ARGV、返回码和并发竞态编写测试；
- `PlayerRouteStore`只实现Gateway登录和GameService生命周期当前使用的方法；
- 其他业务Service查询在线玩家和可靠通知不属于首期实现，出现真实调用方后单独设计。
